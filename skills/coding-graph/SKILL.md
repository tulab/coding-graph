# 编码图谱构建（coding-graph）

## 概述

把需求 / 设计等阶段文本拆成两层节点模型（文本层 / 实体层，Schema 见 §4）并建立关系；本 skill 只写编码图谱增量，执行通道 gg-cli 由 growing-graph skill 提供（接口约定、局部引用 ref、高危删除规则见其 SKILL.md）。

- **汇报要求**：边听边建、静默执行——听用户说话的同时构建，执行期间不逐条汇报，只在任务完成 / 需决策时给一行汇报。
- **批量要求**：每轮提取的节点、关系各并入一次 `gg-cli instance object create` / `link create` 批量提交，不逐条 create。
- **管道要求**：装配 / 增量脚本位于各 skill 基础目录 `scripts/` 下（`<skill_dir>` 由会话加载时给出，直接使用、不要自行查找），命令一律从当前工作目录运行；每轮闭环 装配 → 提取 → 批量提交 → 验证修正。

## 1. 构建工作流

1. **装配**：无参运行 `<skill_dir>/scripts/init_graph.py`，完成身份、建图与类型字典并设为当前图谱。
2. **提取**：按 §3 判断本轮文本属于哪个阶段、是否属于该阶段表达，把属于的部分拆成原子短句节点与关系；拆解要求见 §5。
3. **批量提交**：本轮节点、关系各并入一次 `gg-cli instance object create` / `link create` 提交。
4. **验证修正**：复查连接性与内容，用 `gg-cli graph overview` / `neighbours` 复查，`object/link update` / `delete` 修正。

## 2. 规则与校验

> 汇报 / 批量 / 管道等总体要求见「概述」；以下为构建的硬性约束。

- **构建范围（默认文本层）**：用户没有明确指令时，只做**文本层**图谱（Goal / Feature / Behavior / Rule / Quality / Scenario / Reason / Strategy / Assumption）；一个阶段（如需求 / 设计）完成后**提示用户**是否进行实体层构建，不擅自展开实体层。
- **连接性**：文本层不允许孤立节点或孤立集群——每一个新增节点都必须**链接到一个或多个现有节点**。
- **节点原子性**：一个节点只含一个主语、一个动作、一个对象；文本含"并且/同时/以及"必须拆分。两层同样适用：文本层节点是原子短句，实体层节点是原子实体。
- **关系分层**：文本层内、实体层内、跨层（仅文本层 → 实体层）；跨层边是两层之间唯一连接通道。
- **维度**：`level` / `stage` 等经 `dim` 显式传入（系统不做推断），键 ∈ graph.dims，取值 ∈ 维度字典。
- **属性**：随 object 写入，键 ∈ 该对象类型的属性字典。
- **删除**（继承 growing-graph 的高危规则）：删节点 / 关系前先 `gg-cli graph neighbours` 确认影响面；批量删除须在 batch 里带 `confirm_delete: true` 才会执行；不随手清理可能有用的需求与设计内容。

## 3. 文本语义判断原则

按阶段定义**判断一段文本属于哪个阶段、是否属于该阶段表达**的原则，与 §5 图谱构建要求同样分阶段。当前已定义**需求阶段**（对应 `dim.stage = requirement`，与 §5.1 同一阶段），后续随设计阶段扩展。判断后按 §4.1 选节点类型、按 §5 对应阶段拆解。

### 3.1 需求阶段

一段文本是否属于**需求表达**，须同时满足以下三个原则；任一条不满足即不属于，应从图谱中剔除或改写后再纳入：

1. **主谓宾完整**：具备主语 - 谓语 - 宾语结构，是一个完整短句，不是词组或孤立短语。
2. **抽象与概括**：具备一定的抽象和概括级别——本身还不是可执行实现，需要更具体、细致的设计和实现。
3. **交付标准**：本身可以直接作为最终交付标准——可独立实现、可独立验证。

## 4. 图谱模型

图谱由两个并存的语义层组成，区别在**表现形式**：文本层承载各阶段文本短句，实体层承载从文本中提取的领域实体。两层的连接通道是**跨层边**（仅文本层 → 实体层）。

```
文本层 ────(跨层边: involves / operates_on / realizes / triggered_by)──── 实体层
```

### 4.1 节点类型（15 种）

| Object Type | Object Name | 层 | 性质 | 回答的问题 | 判断标准 |
|---|---|---|---|---|---|
| `Goal` | 目标 | 文本层 | 主线 | 为什么要做 | 无实现细节，表达意图或价值 |
| `Feature` | 功能 | 文本层 | 主线 | 系统提供什么能力 | 用户视角的可见能力 |
| `Behavior` | 行为 | 文本层 | 主线 | 具体怎么表现 | 含触发条件或系统响应 |
| `Rule` | 规则 | 文本层 | 约束 | 有什么约束条件 | 含"必须/不允许/仅当" |
| `Quality` | 质量 | 文本层 | 约束 | 非功能性要求 | 含量化指标 |
| `Scenario` | 场景 | 文本层 | 约束 | 用户怎么用（前端设计）/ 系统须满足什么（后端契约） | 前端设计的使用情境 / 交互流程（什么用户在什么情境下做什么事），或系统对外的行为契约（输入 → 处理 → 输出，限定系统必须提供的服务） |
| `Reason` | 原因 | 文本层 | 依赖 | 为什么做（现状缺口 / 外部归因） | 现状不满足（缺失 / 痛点），或目标 / 功能的外部动因（市场 / 政策 / 用户 / 竞品） |
| `Strategy` | 策略 | 文本层 | 依赖 | 有什么宏观约束 | 事实性语言陈述的设计思想 / 产品边界 / 规律认知 |
| `Assumption` | 假设 | 文本层 | 依赖 | 需求依赖什么前提 | 需求成立所依赖的不确定前提（数据 / 技术 / 环境 / 用户行为等）；前提不成立则该需求需重新评估 |
| `Actor` | 角色 | 实体层 |  | 谁发起操作 | 主语角色 |
| `Action` | 操作 | 实体层 |  | 做什么动作 | 动词 |
| `Domain` | 领域 | 实体层 |  | 被操作的事物 | 名词宾语 |
| `Attribute` | 属性 | 实体层 |  | 领域的特征 | 名词性属性 |
| `Condition` | 条件 | 实体层 |  | 触发上下文 | 条件状语 |
| `Event` | 事件 | 实体层 |  | 触发点或结果 | 事件名词 |

文本层节点按角色分三组：**主线**（Goal / Feature / Behavior——目标、功能、行为，需求分析主线）、**约束**（Rule / Quality / Scenario——规则、质量、场景，限定主线怎么做）、**依赖**（Reason / Strategy / Assumption——原因、策略、假设，为什么做与依赖什么前提）。跨层边与 `constrained_by` 仅从行为性节点（Feature / Behavior / Scenario）出发。

### 4.2 关系类型（15 种）

| Link Type | Link Name | 层 | 方向 | 语义 |
|---|---|---|---|---|
| `motivated_by` | 由…驱动 | 文本层 | 具体 → 抽象 | 该需求因某目标或原因而存在 |
| `decomposes_into` | 拆分为 | 文本层 | 整体 → 部分 | 目标 / 功能 / 场景拆分为子项（总-分） |
| `elaborates` | 细化 | 文本层 | 粗 → 细 | 对同一件事的更详细描述 |
| `specializes` | 特化为 | 文本层 | 通用 → 条件限定 | 在特定条件下的变体 |
| `depends_on` | 依赖 | 文本层 | 双向有序 | 实现或理解上的前置依赖 |
| `conflicts_with` | 与…冲突 | 文本层 | 双向对称 | 两个需求无法同时满足 |
| `constrained_by` | 受…约束 | 文本层 | 行为性节点 → Rule/Strategy | 功能、行为或场景受某规则或策略约束 |
| `performs` | 执行 | 实体层 | Actor → Action | 角色执行操作 |
| `targets` | 作用于 | 实体层 | Action → Domain | 操作作用于对象 |
| `has_attribute` | 具有属性 | 实体层 | Domain → Attribute | 对象具有属性 |
| `applies_to` | 应用于 | 实体层 | Condition → Action/Feature | 条件作用于什么 |
| `involves` | 涉及 | 跨层 | 行为性节点 → Actor | 该需求涉及哪个角色 |
| `operates_on` | 操作对象 | 跨层 | 行为性节点 → Domain | 该需求操作哪个对象 |
| `realizes` | 实现为 | 跨层 | 行为性节点 → Action | 该需求对应哪个具体操作 |
| `triggered_by` | 由…触发 | 跨层 | 行为性节点 → Condition/Event | 触发条件 |

**分层的三条边**：
- 文本层内部（7 条）：垂直边 `motivated_by` / `decomposes_into` / `elaborates` / `specializes`；水平边 `depends_on` / `conflicts_with`；层内跨层 `constrained_by`（源与目标都在文本层：行为性节点 → Rule/Strategy）。`Assumption` 作为需求成立的前提经 `depends_on` 挂接。
- 实体层内部（4 条）：`performs` → `targets` → `has_attribute` 组成实体动作链，`applies_to` 挂接条件。
- 跨层边（4 条）：仅从文本层行为性节点（Feature/Behavior/Scenario）指向实体层节点，是两层之间唯一连接通道；不得出现在实体层内部或反向连接。

**判断要点**：`decomposes_into` vs `elaborates`（拆分后子节点可独立存在 → 前者；只是同一事物补充描述 → 后者）；场景 / 行为辨析（`Scenario` 使用情境或契约——前端交互流程或后端行为契约，`Behavior` 单个系统响应；场景 `specializes` 所属功能、`decomposes_into` 拆成行为步骤、`depends_on` 依赖相关场景 / 节点）；实体动作链是单一语义单位（Actor —performs→ Action —targets→ Domain，`realizes` 连接文本层行为性节点到链上的 Action）；`constrained_by` 是层内跨层，与连接两层的跨层边不同。

### 4.3 维度（Dimension）

图谱建图时声明维度字典并经 `graph.dims` 下发；对象类型按 `level` 标注所属层，实例按 `level` / `stage` 标注。

| 维度 | 维度名 | 取值（code · 显示名） |
|---|---|---|
| `level` | 层级 | `textual` 文本层 · `entity` 实体层 |
| `stage` | 阶段 | `requirement` 需求 · `design` 设计 |

### 4.4 属性类型

属性类型绑定到具体对象类型（该对象类型允许哪些属性键）；实例 `property` 的键须在该对象类型的属性字典内。

| 对象类型 | 允许的属性键 |
|---|---|
| goal | priority 优先级 |
| feature | priority 优先级 · status 状态 |
| behavior | trigger 触发条件 |
| rule | severity 严重度 |
| quality | metric 指标 · target 目标值 |
| scenario | priority 优先级 · result 结果 |
| reason | source 来源 |
| strategy | scope 适用范围 |
| assumption | confidence 置信度 |
| actor | role 角色 |
| action | input 输入 |
| domain | owner 归属 |
| attribute | unit 单位 |
| condition | severity 严重度 |
| event | source 来源 |

## 5. 图谱构建要求

按阶段定义各阶段的构建要求。当前已定义 **需求设计阶段** 与 **产品设计阶段**，**后续还会增加其他阶段**；各阶段以 `dim.stage` 区分（需求设计阶段 → `requirement`，产品设计阶段 → `design`）。

### 5.1 需求设计阶段

> 当前主要构建阶段。围绕**整项工作**建立总-分目标体系，把需求文本从总目标出发逐层拆解成原子短句，用文本层垂直边表达层级与约束。

1. **构造种子节点**：先根据内容概括出**总目标**，建一个 `Goal` 节点作为种子（`type = goal`，`dim.level = textual`）；种子节点就是这个总目标。随后根据对话流推进，适时调整、完善这个总目标。
2. **拆解子目标**：**通常总目标应拆解出多个子目标**，用 `decomposes_into` 表达——总目标 → 子目标；复杂项目甚至会继续拆出**二级子目标**，层级取决于项目复杂度，不要求刻意压平。所有目标都从**业务 / 商业角度**说明（为什么值得做、带来什么价值），不是从软件系统的功能或行为上讲。注意 `decomposes_into` 是**通用拆分关系，不限于目标**：功能可拆子功能、场景可拆交互步骤等。子节点可独立存在才算拆分，同一事物的补充描述用 `elaborates`，特定条件下的变体用 `specializes`。
3. **子需求粒度**：这里说的是**子需求的拆解**，不是目标的拆解。需求拆解的终点是**目标、功能、行为、规则、质量**这些文本节点——需求文本逐层拆到这些粒度，才用得着这套说明。拆解粒度：不停留在笼统的大需求上，也不碎成堆砌的零散短句；以每个节点**可独立实现 / 独立验证**为度。过碎或层级不清时，用 `gg-cli instance object update` / `delete`（数组批量）修正（§1 步骤 4）。
4. **动机挂接**：具体需求因某目标或原因而存在，用 `motivated_by` 指回更抽象的目标 / `Reason` 原因节点（现状缺口，或市场、政策、用户、竞品等外部归因）。
5. **场景**：需求文本描述**用户如何使用**（使用情境 / 交互流程，前端设计侧）或**系统对外须满足的行为契约**（输入 → 处理 → 输出，后端约束侧）时建 `Scenario` 场景节点。场景用 `specializes` 挂到所属功能、`decomposes_into` 拆成行为步骤、`depends_on` 依赖相关场景 / 节点；用 `constrained_by` 约束相关功能 / 行为。
6. **依赖与约束**：实现或理解上的前置顺序用 `depends_on`；受某规则或策略限制用 `constrained_by` 指向 `Rule` / `Strategy`（命令式要求用 Rule，陈述式宏观原则 / 设计思想用 Strategy）；需求成立依赖的不确定前提用 `depends_on` 指向 `Assumption` 假设节点；无法同时满足的用 `conflicts_with` 记录。
7. **原子粒度**：拆到每个节点是原子短句（一个主语 / 一个动作 / 一个对象）即停；文本含"并且/同时/以及"必须继续拆。
8. **连接性**：拆出来的每个节点都必须链接到现有节点——子目标挂到总目标（`decomposes_into`），其余挂到所属父节点或相关节点，不得产生孤立节点或孤立集群。
9. **动态维护**：随着对话推进持续审视已建图谱——出现新需求就**补充新目标**，需求调整就**修改已有目标**，保持总-分关系与当前对话一致。

### 5.2 产品设计阶段
